# السقاية — نظام إدارة الذاتية والأرشفة والتوثيق الإداري

نظام إداري وأرشيفي رقمي داخلي يهدف إلى تنظيم أعمال شعبة الذاتية، وأرشفة الكتب والمعاملات، وإدارة معلومات المنتسبين والباحثين، والسجلات الزمنية، والطلبات، والتقارير، مع توفير صلاحيات وصول وتدقيق مناسبة لطبيعة البيانات الإدارية.

---

## 1. عن المشروع

**السقاية** هو مشروع داخلي مخصص لشعبة الذاتية، بدأ كنموذج أولي محلي لتجربة واجهة النظام وتدفق العمل، ويجري تطويره تدريجيًا نحو منظومة تعتمد على Backend وقاعدة بيانات مركزية وتخزين مركزي للملفات.

يشمل نطاق النظام المستهدف:

* الكتب الواردة والصادرة والداخلية.
* أرشفة المرفقات والوثائق.
* بيانات المنتسبين والباحثين.
* الإجازات والأذونات والسجلات الزمنية.
* المواقف اليومية.
* التكليفات والدورات.
* الطلبات وإجراءات الموافقة.
* التذكيرات المرتبطة ببعض السجلات.
* التقارير والإحصائيات.
* سجل التدقيق Audit Log.
* سجل الاطلاع View Log.
* البحث والوصول إلى المعلومات وفق الصلاحيات ونطاق الوصول.

---

## 2. حالة المشروع الحالية

المشروع يمر بعملية انتقال منظمة من النموذج الأولي إلى النظام المستهدف.

### Phase 0 — Baseline & Architecture Lock

**الحالة: مكتملة**

تم في هذه المرحلة:

* تثبيت النسخة الأصلية من النموذج الأولي كنقطة مرجعية.
* إنشاء مستودع Git.
* معالجة أخطاء البناء الموجودة في النسخة الأساسية.
* إزالة الاعتماديات والملفات غير المستخدمة.
* تنظيف بيانات الاختبار من الأسماء الشخصية.
* توثيق حالة المشروع الحالية.
* تثبيت المعمارية والخطة والقواعد المرجعية للمراحل التالية.

المرحلة الحالية بعد Phase 0 هي:

**Phase 1 — Domain Models**

ولا يتم تنفيذ مرحلة لاحقة قبل إكمال المرحلة الحالية واختبارها وتثبيتها.

## 3. المعمارية

المعمارية المستهدفة للنظام هي:

```text
React SPA
    │
    ▼
REST API / Backend
    │
    ▼
Node.js + Express + TypeScript
    │
    ├── Authentication
    ├── Authorization / RBAC
    ├── Access Scope
    ├── Audit Logs
    ├── View Logs
    ├── Concurrency Control
    └── Scheduled Operations
    │
    ├───────────────┐
    ▼               ▼
PostgreSQL     Central File Storage
```

في النسخة المستهدفة يكون الـBackend هو نقطة التحكم في البيانات والصلاحيات، ولا تعتبر واجهة React مصدرًا للحقيقة أو طبقة أمان.

للتفاصيل الفنية والمعمارية، راجع:

`ARCHITECTURE.md`

## 5. مبادئ التطوير

يعتمد المشروع على مجموعة من المبادئ الأساسية:

1. المعمارية والخطة قبل التنفيذ.
2. صحة البيانات أهم من سرعة التنفيذ.
3. المحافظة على البيانات الموجودة وعدم فقدانها.
4. تنفيذ مرحلة واحدة في كل مرة.
5. عدم تنفيذ وظائف تخص مراحل مستقبلية.
6. عدم اختراع قواعد عمل غير معتمدة.
7. فصل هوية المستخدم عن بيانات الموظف.
8. جعل الأمان والصلاحيات في الخادم عند الانتقال إلى المعمارية المستهدفة.
9. استخدام بيانات اختبار أثناء التطوير وعدم خلطها بالبيانات الحقيقية.
10. اختبار كل مرحلة قبل تثبيتها والانتقال إلى التالية.

التفاصيل الكاملة موجودة في:

`PROJECT_RULES.md`

## 6. التشغيل المحلي الحالي

### المتطلبات

يتطلب تشغيل النموذج الأولي بيئة Node.js مناسبة للمشروع.

### تثبيت الاعتماديات

```bash
npm install
```

أو، عند العمل من نسخة تحتوي على `package-lock.json`:

```bash
npm ci
```

### تشغيل بيئة التطوير

```bash
npm run dev
```

### فحص المشروع

```bash
npm run lint
```

### بناء نسخة الإنتاج

```bash
npm run build
```

## 7. النموذج الأولي الحالي

النسخة الحالية من المشروع هي Prototype وليست النظام النهائي.

تعتمد النسخة الحالية على:

* React.
* TypeScript.
* Vite.
* Tailwind CSS.
* تخزين محلي عبر `localStorage`.
* بيانات اختبار محلية.
* خدمات محلية داخل التطبيق.
* نموذج مصادقة تجريبي.

هذه المكونات موجودة لغرض التطوير والاختبار ولا تمثل المعمارية النهائية للنظام.

وبالأخص:

* `localStorage` ليس قاعدة البيانات النهائية.
* المرفقات المخزنة بصيغة محلية ليست آلية التخزين النهائية.
* المصادقة الحالية ليست نظام المصادقة الإنتاجي.
* الصلاحيات الحالية في الواجهة لا تعتبر بديلًا عن التفويض server-side.
* بنية الـPrototype لا تُعتبر إلزامًا للبنية النهائية إذا تطلبت المراحل اللاحقة إعادة تنظيمها.

## 8. بيانات التطوير

يجب استخدام بيانات وهمية أثناء التطوير والاختبار.

لا ينبغي إدخال أو ترحيل البيانات الحقيقية إلى النظام قبل استكمال المتطلبات المتعلقة بـ:

* قاعدة البيانات.
* التخزين المركزي للملفات.
* المصادقة.
* الصلاحيات.
* سجل التدقيق.
* النسخ الاحتياطي والاستعادة.
* التحقق من سلامة البيانات والترحيل.

## 9. منهج تنفيذ المراحل

كل مرحلة تمر بالدورة التالية:

```text
قراءة الخطة والوثائق
        ↓
تحديد نطاق المرحلة
        ↓
التنفيذ
        ↓
الاختبار
        ↓
TypeScript / Lint / Build / Tests
        ↓
مراجعة النتائج
        ↓
Git Checkpoint
        ↓
التوقف
```

لا يبدأ تنفيذ المرحلة التالية إلا بعد تثبيت المرحلة الحالية ومعالجة المشكلات المتعلقة بها.

## 10. دور Cline

يستخدم Cline كأداة تنفيذ داخل بيئة التطوير.

قبل تنفيذ أي مرحلة يجب أن يقرأ:

* `ALSQAYA_PLAN.md`
* `PROJECT_RULES.md`
* `ARCHITECTURE.md`
* الوثائق المتعلقة بالمرحلة الحالية
* تقرير المرحلة السابقة عند الحاجة

ويجب أن يلتزم بنطاق المرحلة المحدد وألا ينفذ وظائف من مراحل مستقبلية.

---

## 11. النشر المستهدف

يستهدف النظام في مرحلته الأولى التشغيل داخل شبكة LAN المحلية، بحيث يستطيع المستخدمون المصرح لهم الوصول إليه من أجهزة الحاسوب والهواتف ضمن الشبكة.

وتبقى إمكانية الوصول الخارجي وHTTPS والتشغيل عبر الإنترنت ضمن مراحل مستقبلية منفصلة، وليست شرطًا لإكمال نسخة LAN الأولى.

---

## 12. ملاحظة مهمة

السقاية نظام داخلي قيد التطوير، وليس بديلًا عن الأرشيف الرسمي أو السجلات الرسمية المعتمدة.

الهدف هو توفير منظومة رقمية مساعدة ومنظمة لإدارة المعلومات والأرشفة والمتابعة داخل شعبة الذاتية، مع المحافظة على إمكانية التحقق من البيانات والوثائق والرجوع إلى السجلات الرسمية عند الحاجة.
