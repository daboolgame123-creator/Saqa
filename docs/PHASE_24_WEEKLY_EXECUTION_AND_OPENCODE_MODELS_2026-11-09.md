## 1. ما يجب أن تعرفه أي محادثة جديدة

- اسم المشروع **السقاية ALSQAYA**: نظام مؤسسي داخلي (LAN) للأرشفة وإدارة الذاتية؛ React 19 + TypeScript + Vite، Express/Node، PostgreSQL، تخزين مركزي للمرفقات.
- تم **دمج** PR #51 على `phase-10-api-data-layer` عند `d04ec752`. الدمج لم يغيّر شجرة ملفات RC2، واختبارات SHA الدمج 9/9 SUCCESS. الاختبارات الشاملة على نسخة مطابقة برمجيًا: 863 ناجحة / 0 فاشلة / 1 متخطاة، على [GitHub Actions #42490656873](https://github.com/daboolgame123-creator/Saqa/actions/runs/42490656873).
- **PR #1** إلى الفرع الافتراضي `phase-0-baseline` لا يزال مفتوحًا/غير مدمج عند إعداد هذه الخطة؛ لا تدمجه تلقائيًا.
- البوابة `src/core/reportReleaseGate.ts`: `OFFICIAL_REPORTS_RELEASE_APPROVED = false`؛ التقارير الرسمية `/api/reports*` تعطي HTTP 503 `REPORTS_UNAVAILABLE`. **ممنوع تغييرها أو تقديم التقارير على أنها متاحة** دون موافقة مالك منفصلة ومراجعة اختبارات على SHA محدد وقبول الخادم.
- واجهة `ReportsCandidateView` موجودة ومربوطة بشرط بوابة مغلقة؛ الواجهة المرئية الرسمية الحالية كتالوج/تنبيه ومعاينة شهرية غير معتمدة. **لا تعِد بناءها من الصفر**.
- خدمة `reportOwnAcknowledgements.ts` لتقرير إقرارات الموظف نفسه وتصدير XLSX داخلية **غير موصولة رسميًا**، منفصلة عن تقرير الإعمامات الإداري المميّز.
- **الباحثون والأساتذة**: لا يوجد مصدر مستقل معتمد؛ فشل صريح `ReportNotImplementedError` وليس بيانات صفرية مزيفة.
- سقف نتائج التقرير `MAX_REPORT_ROWS=2000`: 2001 فشل آمن؛ لا يجوز عرض إجمالي مبتور.
- رمز التفعيل الصادر عن **المدير حضوريا C15** صالح **60 دقيقة**؛ OTP الذاتي القديم 5 دقائق. لا تغيّر هذه السياسة خطأً.
- أداة **إنشاء أول مدير** موجودة ومدققة في اختبارات PostgreSQL اصطناعية؛ قبول التشغيل على الخادم وإجراءات المشغل لم يثبتا بعد.
- **القبول المؤسسي متبقٍ:** HTTPS/LAN، ضوابط مضيف Docker والصورة الثابتة digest والخطوط، فحص صفحات PDF العربية، استعادة قاعدة PostgreSQL والمرفقات معًا، إعداد `ALSQAYA_REPORT_TIME_ZONE`، قبول أول مدير وتشغيل الاختبارات على الخادم. لا تستخدم بيانات حقيقية في CI.
- آخر مراجعة بعد الدمج موثقة في [PR #51 comment](https://github.com/daboolgame123-creator/Saqa/pull/51#issuecomment-6736636144).
- **قاعدة المستخدم:** التحليل والخطة قبل التنفيذ، ثم تنفيذ **عدة مهام مترابطة** بكفاءة، ثم اختبار فعلي، مراجعة مستقلة حيث تبررها المخاطر، توثيق SHA/CI، والإغلاق. لا نفتح سلسلة تحسينات لا تنتهي ولا نكرر مراجعات مستقلة للكود غير المتغير.

## 3. كيفية تخصيص النماذج (توزيع مبدئي قابل للتعديل)

تخصيص الأدوار أدناه **اختيارات تشغيلية تجريبية وليست تصنيفًا علميًا موثقًا لأداء النماذج**. اعتمد جودة النتيجة وقياس التكلفة/الزمن الفعلي في OpenCode؛ بدّل النموذج إذا لم يحقق معيار المهمة.

| نوع المهمة | النموذج المقترح أولًا | التفكير | قواعد الاستخدام |
|---|---|---|---|
| معمارية/تحديد فروق Phase 24 | `GPT-6 Astra` | `High`؛ `Xhigh` عند معضلة مؤكدة | تحليل محدود النطاق؛ قرار قبل التنفيذ |
| برمجة UI/React وربط تجريبي | `GPT-6.1 Sol` | `Medium`، تصعيد `High` عند عائق | تنفيذ عدة تعديلات مترابطة واختبارات مركزة |
| مراجعة أمان RBAC وViewLog | `GPT-6.1 Terra` | `High` أو `Xhigh` عند ثغرة مثبتة | مراجع مستقل عن منشئ التغيير؛ فرق SHA فقط |
| PostgreSQL ونسخ/استعادة تجريبية | `GPT-6 Astra` أو `GPT-6.1 Terra` | `High` | بيانات اصطناعية، خطط استعادة غير مدمرة |
| PDF/Excel وDocker المرشح | `GPT-6.1 Sol` | `Medium`، مع مراجعة `GPT-6.1 Terra High` لمخاطر العزل | لا تحسينات تجميلية غير مرتبطة بالقبول |
| اختبار CI وإصلاح فشل محدد | `GPT-6.1 Sol Fast` أو `GPT-6 Astra Fast` | `Low`/`Medium` للتشخيص السهل؛ `High` للعطل المعقد | تحقق من سجلات الاختبار نفسها |
| التوثيق، ملخصات الانتقال، قوائم القبول | `GPT-6 Luna Fast` أو `GPT-5.6 Luna Fast` | `Low` أو `Medium` | لا تُكرر قراءة آلاف الأسطر |
| التكامل النهائي/قرار غلق حزمة | `GPT-6 Astra` | `High` | مراجعة معايير القبول وأدلة exact SHA |
| عائق تقني/أمني مستعصٍ بعد محاولات مثبتة | نموذج مناسب متاح مثل `GPT-6.1 Terra` | `Xhigh` ثم `Max` **فقط عند الحاجة الموثقة** | حدّد المشكلة وقياس الفائدة قبل رفع الاستهلاك |

- اختر `Fast` للمهام المحددة عندما تعطي نتيجة مقبولة فعلًا، دون افتراض مسبق أن كل Fast أرخص أو أدق.
- لا يُستخدم `Max` بشكل تلقائي؛ حافظ على رصيد للقرار/التكامل الحرج. نسب الاستهلاك **ديناميكية** بلا سقف نسب ثابتة، لكن سجّل الاستخدام الحقيقي بعد كل حزمة إن أظهره OpenCode.
- **OpenCode Plan** للتحليل قبل كتابة أي كود، و**Build** بعد استقرار الخطة ومعايير القبول. OpenCode لا يدمج PR من تلقاء نفسه.
- بيئة التنفيذ الأساسية: ChatGPT + أدوات GitHub؛ OpenCode للدُفعات الكبيرة أو المراجعة المستقلة المطلوبة، مع منع التعديل المتوازي على الملفات ذاتها بلا تنسيق.
- في بداية كل جلسة بيّن: «أنا أعمل على …، وOpenCode يعمل على …»، مع أسماء الفروع وأحدث SHA/CI.

## 4. المهام الست مرتبة حسب الأولوية

### 24-A — تثبيت نطاق Phase 24 والفجوات الحقيقية (المهمة الأولى)
- قارِن الواقع مع المتطلبات المعتمدة؛ أصدر مصفوفة: «موجود ومختبر / مرشح محجوب / ناقص المصدر / يحتاج مضيف».
- راجع آلية البوابة بين UI وExpress، ومصدر الباحثين والأساتذة، ومسار ViewLog الخاص بالموظف.
- **القبول:** قائمة مهام محددة مدعومة بمسارات وأدلة، دون مراجعات مُعادَة أو توسع غير مبرر.

### 24-B — جاهزية الواجهة الرسمية المرشحة (دون فتح التقارير)
- اختبر UI-10 الحالية: أنواع التقارير، الفلاتر، المعاينة والتصدير، تبديل الحسابات، الطلبات المتأخرة وموانع تسرب الجلسة.
- أصلح الخلل **المثبت فقط** واختبر React + Chromium + PostgreSQL اصطناعية عند الحاجة.
- **القبول:** اختبارات UI سلبية وإيجابية، لا استبدال `ReportsView` فعليًا ولا رفع HTTP 503.

### 24-C — المسار المرشح لإقرارات الموظف نفسه
- ادرس ربط القارئ الداخلي `readOwnCircularAcknowledgements` وخدمة Excel عبر مسار محمي منفصل، **خلف بوابة نشر مغلقة**.
- اختبر محاولات قراءة إقرارات شخص آخر، هوية موظف مفقودة، ViewLog تاريخية ملتبسة، وحصر بيانات التصدير.
- **القبول:** عدم كشف أسماء/إجماليات الزملاء، وعدم استخدام صلاحية تقرير الإدارة، وفحص PostgreSQL/HTTP على المسار الاختباري فقط.

### 24-D — جاهزية النسخ الاحتياطي والاستعادة والمهاجرات
- إعداد/إثبات استعادة **PostgreSQL والمرفقات معًا** على بيانات اصطناعية، مع checksums وتطابق السجلات وعينات الصلاحيات.
- التحقق من مهاجرة `0015` (فهرس عادي غير `CONCURRENTLY`، يتطلب تقدير نافذة صيانة)، والحماية من `db:rollback` المدمّر.
- **القبول:** دليل سيناريو استعادة متكرر في مختبر غير مؤسسي؛ لا عمليات على بيانات حقيقية.

### 24-E — جاهزية Excel/PDF قبل الاعتماد
- استثمار العامل المعزول الموجود، والتحقق من عدم اقتطاع الصفحات أو الإقرارات، العربية واتجاه النصوص، وتوافق إجمالي/تفاصيل SQL/XLSX/PDF.
- إعداد Manifest بعناصر صورة Docker وdigest، الخط العربي/ترخيصه، وقيود الموارد وعزل الشبكة. لا ادعاء موافقة على المضيف قبل فحصه.
- **القبول:** عينات اصطناعية واختبارات موثقة وقائمة قبول المضيف المتبقية؛ لا فتح PDF رسمي.

### 24-F — التكامل والاختبارات والإغلاق المرحلي
- جمع الفروق المقبولة في فرع مرشح منفصل، والتحقق من عدم إدخال تغييرات غير مطلوبة، وتشغيل CI على SHA دقيق.
- مراجعة أمنية مستقلة **للتغييرات الجديدة فقط**، إصلاح عوائق حقيقية، إعادة الاختبارات المتأثرة، وتوثيق قرار `READY_FOR_PREPROD_REVIEW` أو `NO_GO`.
- **القبول:** PR مرشح، CI متحقق، مصفوفة مخاطر متبقية، وعدم الدمج أو النشر بلا إذن.

## 6. شروط عدم التجاوز في كل مهمة

1. لا رفع `OFFICIAL_REPORTS_RELEASE_APPROVED = false` أو إزالة HTTP 503 بلا إذن مستقل وSHA واختبارات وموافقة مضيف مؤسسي.
2. لا دمج PR #1 ولا تغيير الفرع الافتراضي `phase-0-baseline` ولا نشر فعلي تلقائي.
3. لا استخدام بيانات حقيقية أو أسرار في CI أو محادثات أو عينات PDF.
4. لا افتراض أن أسماء الباحثين/الأساتذة يمكن تعويضها عن سجلات الموظفين.
5. لا توسيع صلاحيات الدور أو نطاق الرؤية بسبب تسهيل واجهة.
6. لا إغلاق مزعوم دون تفاصيل فرع وSHA ورابط CI ونتيجة اختبارات فعلية.
7. **مرحلة 23 مغلقة برمجيًا**: لا تعاد إلا لخلل مثبت في الشفرة المدمجة. عمل اليوم تحت Phase 24.
8. لا تَعِد باكتمال host acceptance من محاكاة CI.
