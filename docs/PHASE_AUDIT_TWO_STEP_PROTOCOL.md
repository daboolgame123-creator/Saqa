# السقاية — بروتوكول تدقيق كل مرحلة على خطوتين وتوزيع العمل مع OpenCode

**تاريخ الاعتماد التوثيقي:** 2026-11-23  
**النوع:** سياسة تنفيذ لتدقيق المراحل السابقة والجديدة؛ لا تغيّر `ALSQAYA_PLAN.md` أو قواعد الأعمال أو صلاحيات الوصول.  
**المسار المعتمد بطلب صاحب المشروع:** فحص المراحل **بالترتيب من الأولى إلى آخر ما وصلنا إليه**، وتحديد الأعطال المثبتة وإصلاحها قبل الانتقال إلى التالية، دون إعادة بناء كل مرحلة من الصفر.

## 1. القاعدة المختصرة

كل **مرحلة N** تمر بخطوتين واضحتين، ثم قرار تحقق/انتقال:

- **N-A — الفحص والتوزيع (Inspect & Triage):** اقرأ نطاق المرحلة في الخطة والشيفرة الفعلية وواجهاتها واعتمادياتها؛ أثبت العيوب، صنّف أثرها، حدّد من ينفذ كل إصلاح: `CHAT` أو `OPENCODE` أو `OWNER/HOST`. لا تفتح تحسينات غير لازمة.
- **N-B — الإصلاح والتحقق (Fix & Verify):** يتولى ChatGPT **بنفسه** كل عمل قادر على تنفيذه واختباره بأدواته الحالية (GitHub/CI/مستندات/كود). يُسلَّم إلى OpenCode **فقط** الجزء الذي يتطلبه فعلاً، مع مهمة محددة ومقياس نجاح. اختبر أثر الإصلاح على المراحل السابقة.
- **قرار بعد N-B:** للمساعد الاختيار بين **فحص موجّه إضافي** لمخاطرة/نقطة لم تُحسم، أو **إغلاق مراجعة الكود والانتقال إلى N+1** إذا اكتملت معاييرها. الاختيار لا يبرر القفز فوق خلل حرج أو اختبار إلزامي فاشل. الفحص الإضافي دورة تحقق قصيرة داخل N، **وليس مرحلة تطوير جديدة**.

لا يُطلب إذن جديد من المالك في كل خطوة تدقيق عادية؛ يلزم إذنه **قبل** الدمج، أو الحذف/الترحيل الحقيقي، أو استخدام بيانات حقيقية، أو تعديل صلاحيات/سياسة أمنية، أو تكليف OpenCode فعليًا، أو رفع حظر التقارير.

## 2. الخطوة N-A: فحص بنية المرحلة وتحديد المسؤول

1. **حالة البداية:** اقرأ `AGENTS.md` و`ALSQAYA_PLAN.md` وبروتوكولات البيئة/التسليم، ثم تحقّق من GitHub: `base`, `HEAD`, PRs، CI، والفروع المحلية التي أبلغ بها المستخدم. لا تفترض أن PR أخضر مدمج.
2. **الحدود:** استخرج المتطلبات الأصلية ومعيار إغلاق المرحلة. اذكر الملفات والمسارات وواجهات API والجداول والهجرات والمكتبات المتأثرة؛ حدّد الاختبارات القائمة.
3. **فحص طبقات التوافق:** Domain/DTO/validation/controller/service/repository/SQL/React، شمول الصلاحيات ونطاق الرؤية، المعاملة/الrollback، تحديث الواجهة، المرفقات، والتحويل بين الـAPI ونموذج المجال بحسب صلة كل طبقة.
4. **المكتبات:** اقرأ `package.json` و`package-lock.json` وNode/TypeScript؛ اختبر البناء على النسخ المثبتة أولاً. أي تجربة `latest` تكون في Runner مؤقت وبلا تحديث تلقائي للـlockfile. لا تُعتبر نسخة أحدث شرطًا للترقية ما لم يثبت عائق أو ثغرة؛ عدم توافق TypeScript 7 مؤجل كملف عام حتى يثبت الحل.
5. **اجعل كل عيب قابلًا للإثبات:** مسار الملف/دالة، سيناريو الفشل، أثره، اختبار موجود أو اختبار انحدار سيُضاف، ومدى صحة الاستنتاج. `SUSPECTED` ليس `CONFIRMED`.
6. **فرز العيوب حسب العائق:** `P0` تسريب/فقد أو فساد بيانات/تجاوز صلاحيات؛ `P1` فشل وظيفي مؤثر أو حاجز نشر؛ `P2` تحسين غير حاجز غالبًا. لا يُغلق `P0/P1` فعلي غير مُعالج؛ سجّل `P2` ولا تجعله دوامة عمل.
7. **تعيين المسار والبيئة:** لكل بند `CHAT`, `OPENCODE`, `HYBRID`, أو `BLOCKED/OWNER`، مع سبب ملموس وحدود الوصول وأدلة القبول.
8. **مخرج N-A:** جدول قرار قصير في تقرير المرحلة، وقائمة إصلاحات N-B مع معرفات مستقلة (`P11-01` مثلاً)؛ لا تبدأ كتابة واسعة قبل اكتمال هذا الفرز.

### صيغة جدول الفرز الإلزامية

| ID | المشكلة/الدليل | الخطورة | المنفّذ | البيئة/الفرع | اختبار القبول | الحالة |
|---|---|---|---|---|---|---|
| PNN-01 | رابط الملف + سيناريو قابل للإعادة | P0/P1/P2 | CHAT/OPENCODE/HYBRID/OWNER | بيئة معزولة | نتيجة محددة | CONFIRMED/SUSPECTED/BLOCKED/VERIFIED |

**مبدأ التوزيع:** لا تنقل مهمة إلى OpenCode لمجرد أنه يستطيع كتابتها. على ChatGPT تنفيذ العمل الممكن عبر أدواته؛ OpenCode مخصص لما **لا يمكن إغلاق دليل قبوله** هنا، أو مراجعة مستقلة في موضع أمني حساس، أو تنفيذ محلي يتطلب جهاز المستخدم.

## 3. الخطوة N-B: التنفيذ والاختبار والإغلاق

1. أنشئ فرع إصلاح مستقلًا عن أساس Git مُتحقق منه، أو استخدم فرعًا سبق اعتماده للمهمة؛ لا تكتب على فرع OpenCode أو تعديلات المستخدم المحلية.
2. نفّذ **أصغر تغيير يعالج عيبًا مثبتًا**؛ اختبارات انحدار سلبية وإيجابية قبل توسيع الحل. لا تعطّل 401/403 أو `503 REPORTS_UNAVAILABLE` أو تُضعف الأمان لتمرير الاختبارات.
3. اختبر المدخلات/المخرجات، الحدود والفشل، وعزل المنتسبين، وعدم تكرار النتائج، وحفظ الـround-trip، وعمليات rollback عند الحاجة. لا بيانات حقيقية في fixture.
4. شغّل الاختبارات المناسبة على الكود النهائي: TypeScript، build، الوحدات المتأثرة، API وPostgreSQL الاصطناعية، ثم اختبارات الخادم/DB/API الشاملة عند التأثير المشترك. اعتمد **نتيجة آخر SHA فقط**.
5. راجع التداخل: اختبر تركيب إصلاح المرحلة N **مع مرشحي جميع المراحل الأقدم** في clone/Runner مؤقت. نجاح CI لفرع معزول لا يعني أن كل PRs متكاملة رسمياً.
6. أفصح عن المكتبات: `locked PASS`، `latest probe PASS/FAIL`، `audit high/moderate`، دون ترقية تلقائية غير ضرورية.
7. افتح `Draft PR / NO MERGE` مع عيوب مثبتة وحلول واختبارات وSHA/Run والقيود؛ لا تسوّغ الدمج لمجرد نجاح CI.
8. حدّد نتيجة المرحلة بوضوح:
   - `CODE_AUDIT_CLOSED`: كل أخطاء الكود الحاجزة أثبت إصلاحها على SHA معيّن، والاختبارات المطلوبة نجحت.
   - `PARTIAL / WAITING_OPENCODE`: كود مكتوب لكن اختبار أو مراجعة إلزامية خارجية غير منجزة.
   - `HOST_ACCEPTANCE_PENDING`: الشيفرة مراجعة لكن التشغيل الفعلي/الشبكة/الجهاز/النسخ لم يُعتمد بعد.
   - `MERGED`، `UAT_ACCEPTED`، `RELEASE_GO` حالات **مستقلة** لا تترتب تلقائيًا على `CODE_AUDIT_CLOSED`.
9. إذا كان فحص إضافي سيغيّر قرار الإغلاق (عيب محتمل فعلي أو خطر مرتبط)، نفّذ **فحصًا واحدًا موجّهًا** واختبارًا، ثم أعد الحكم. وإلا انتقل مباشرة إلى فحص المرحلة التالية؛ لا تفتح دورة تحسين غير محددة.

**بوابة الانتقال:** ننتقل إلى N+1 في **تسلسل مراجعات الكود** فقط بعد `CODE_AUDIT_CLOSED` للمراجعة N، أو بعد توثيق مانع خارجي مستقل غير مؤثر على سلامة تدقيق N+1 مع عدم الادعاء بالإغلاق؛ لا يُتجاوز مانع أمني يتصل بالمرحلة التالية. **هذا لا يمنح إذن تشغيل أو دمج.**

## 4. متى يكون OpenCode ضروريًا؟

| نوع العمل | المنفّذ الافتراضي | التصعيد إلى OpenCode عندما... |
|---|---|---|
| قراءة GitHub، تحليل الكود، اختبارات وحدات، إصلاحات محددة وCI | CHAT | لا تتاح الملفات/الأدلة اللازمة أو تُطلب مراجعة مستقلة |
| كتابة أو تعديل ملفات محلية لم تُرفع (UI-04/A2.3 مثلاً) | OPENCODE على جهاز المالك | يلزم الوصول للمجلد المحلي والتعامل مع العمل غير الملتزم |
| متصفح حقيقي على Windows، تسجيل دخول بأدوار متعددة، تنزيل مرفقات | OPENCODE + اختبار المالك | لا تكفي CI لمحاكاة التفاعل/البيئة الفعلية |
| تجارب PostgreSQL المهاجرة أو التراجع على **قاعدة اصطناعية مؤقتة** | CHAT إذا تكفي CI؛ وإلا OPENCODE | تتطلب تجربة Windows/بيئة محددة أو صلاحية محلية |
| نسخة من بيانات المؤسسة، staging أو ترحيل/استعادة حقيقية | OWNER + OPENCODE بعد موافقة محددة | لا يُسمح حتى بخطوة مغيرة دون تأكيد هوية الهدف ونسخة قابلة للاستعادة |
| مراجعة أمنية مستقلة لتغييرات Auth/RBAC/Access/تقارير | OPENCODE كمدقّق مستقل عند بلوغ بوابتها | يُراجَع SHA نهائي **بلا تعديل فرع التنفيذ أثناء المراجعة** |
| تعارض دمج متشعب/اختبارات تكامل في clone محلي | CHAT إن أمكن GitHub CI؛ وإلا OPENCODE | يلزم فحص العمل المحلي والـworktree أو حل تعارض موثق |
| اعتماد خادم LAN، الملفات، Docker/PDF، النسخ والاستعادة | OPENCODE + مسؤول الخادم + المالك | وجود متطلبات تشغيل لا يمكن إثباتها في CI |

**حالة OpenCode لا تُفترض:** اكتب `NOT_ASSIGNED` أو `STATUS_UNKNOWN` حتى يبلّغ المالك بالتكليف والفرع/النتيجة. لا تدّع أنه يختبر في الخلفية.

## 5. بروتوكول تسليم مهمة واحدة إلى OpenCode

### قبل إرسال المهمة
1. حدّد **ID واحدًا** ونطاق ملفات واضحًا، والفرع أو HEAD الذي سيفحصه، والمعيار الذي يمنع إغلاقها.
2. ابدأ OpenCode بوضع **Plan** إذا كانت المهمة تحليلًا أو مراجعة أو لها أثر أمن/بيانات/دمج؛ استخدم **Build** بعد الاتفاق على النطاق والخطة عندما يكون التنفيذ مطلوبًا فعلاً. لا تعطه أمر Build لعملية حذف/ترحيل حقيقية دون إذن منفصل.
3. اكتب قيودًا صريحة: لا `push/merge`، لا تغيير بيانات المؤسسة، لا اتصال بـ`alsqaya_staging`، لا تعديل ملفات مستخدم غير مصرح بها، لا تعطيل `503`، وعدم مشاركة أسرار في logs.
4. اطلب أولاً `git status --short` و`git rev-parse HEAD` وقراءة الملفات/الـdiff **دون تعديل**؛ إذا كانت working tree غير نظيفة، يفصل العمل بأمان ولا يحذف أي عمل سابق.
5. لا تُكلفه نفس الملفات أثناء تعديل CHAT لها؛ تثبت ملكية المهمة والفرع عند توزيعها.

### قالب تكليف جاهز قابل لإعادة الاستخدام

```text
مشروع: ALSQAYA / Saqa
المهمة: <ID> — <عنوان محدد>
المرحلة: <N-A فحص فقط / N-B تنفيذ وإصلاح>
المستودع/الفرع/HEAD: <الروابط والقيم الدقيقة بعد التحقق>
الحالة السابقة: <الاختبارات المؤكدة وما لم يختبر>
الهدف والأثر: <عيب مثبت + سيناريو تكرار>
النطاق المسموح: <مسارات/ملفات/خدمة محددة>
الممنوع: لا بيانات حقيقية؛ لا قاعدة alsqaya_staging؛ لا حذف/ترحيل حقيقي؛
        لا push/merge؛ لا رفع حاجز 503؛ لا تغيير فرع/ملفات زميل.
قبل التنفيذ: اقرأ AGENTS.md وخطة المرحلة وبروتوكول التدقيق؛
            نفّذ git status --short وgit rev-parse HEAD؛
            اكتب خطة مختصرة واختبارات القبول، ثم ابدأ ضمن النطاق فقط.
الاختبارات: <أوامر دقيقة بعد مراجعة scripts ووجهة PostgreSQL>
دليل القبول: <PASS/FAIL على SHA دقيق؛ اختبار سلبي وإيجابي؛
             عدم تسريب/فقد أو نقل ملكية؛ لقطات UAT عند اللزوم>
التسليم: تقرير قصير ID، الملفات المتغيرة، SHA، أوامر/نتائج
         الاختبارات، ما لم يُختبر، المخاطر، وما يلزم للمتابعة.
توقف عند نهاية المهمة؛ لا تبدأ المهمة التالية أو تدمج أي شيء.
```

### عند رجوع OpenCode
- اقرأ تقريره مع `git diff` و`status` وSHA وسجلات الاختبارات؛ تحقق بنفسك من النتيجة المتاحة.
- **لا تعتبر الرسالة «تم» دليلًا**؛ `Plan complete` ليس `Code fixed`، و`tests written` ليست `tests passed`.
- إن كشف خللًا جديدًا P0/P1: أعده إلى جدول فرز المرحلة الحالية، ونفّذه في المسار الأنسب؛ وإن كان P2 غير حاجز دوّنه ولا توسّع بلا سبب.
- عند اختلاف النتيجة عن CI أو تعذر UAT سجّل `WAITING_EXTERNAL` مع سبب محدد؛ لا تغلق بالظن.

## 6. مخرجات كل محادثة ومتى ننتقل

**بداية العمل:** `CHAT: مرحلة/خطوة/فرع`؛ `OPENCODE: آخر مهمة مؤكدة أو NOT_ASSIGNED`؛ `المانع` إن وجد.

**بعد N-A:** ملخص قصير بالمشكلات المؤكدة وعددها، توزيع `CHAT/OPENCODE`، ثم تنفيذ N-B مباشرة قدر الإمكان.

**بعد N-B:** ما أُصلح؛ اختبارات `pass/fail/skip` على SHA ورابط PR؛ حالة الإغلاق؛ والحكم التالي `RECHECK N` أو `AUDIT N+1`. لا تُرهق المحادثة بتقرير مكرر؛ التفاصيل في ملف المرحلة والـPR.

**ملف المتابعة الواحد** لمهام OpenCode: [`OPENCODE_AUDIT_HANDOFF_REGISTER.md`](OPENCODE_AUDIT_HANDOFF_REGISTER.md). تُحدّث الحالة بعد وجود **تقرير/دليل** لا بعد استنتاج من نشاط GitHub.

## 7. حواجز لا تتغير

- `503 REPORTS_UNAVAILABLE` في Phase23 يبقى مفعّلاً حتى قبول منفصل.
- لا تغيير على بيانات منتسب حقيقية أو أسرار أو صلاحيات أو بيئة الإنتاج دون اعتماد واضح؛ الأولوية لاختبارات اصطناعية.
- نسخ احتياطي قابل للتحقق قبل أي عملية مغيرة مصرح بها على staging/production، وفحص هوية قاعدة البيانات/المسار/المنفذ مرتين؛ لا تراجع تدميري افتراضي.
- كل فروع تدقيق Phases 1–10 مسودات **غير مدمجة** عند توثيق هذا البروتوكول؛ لا تخلط نجاح CI بوجود الإصلاح على جهاز المستخدم.
- لا إعادة فتح مراجعة مرحلة أُغلقت كوديًا بلا دليل جديد يؤثر في سلامة التكامل أو القبول؛ عند الحاجة يسجل **إصلاح رجعي محدد** ثم نعود إلى المرحلة الحالية.

## 8. بطاقة تشغيل إلزامية لكل مرحلة (من N-A إلى قرار الانتقال)

لا يُعاد إنشاء خطة كبيرة لكل مرحلة. املأ بطاقة واحدة ضمن تقريرها، ويُحدَّث سجل OpenCode فقط عند الحاجة الفعلية:

~~~text
Phase: N / العنوان / نطاق § في ALSQAYA_PLAN
Baseline branch + SHA:
Related PRs + SHA / unmerged changes:
N-A / architecture inspected: Domain, Routes/API, DB, UI, RBAC, tests
N-A / findings: ID + severity + CONFIRMED or SUSPECTED + reproduction
N-A / owner per finding: CHAT | OPENCODE | OWNER/HOST, and why
N-B / changed files + fixed SHA + regression test:
N-B / lint, build, server, db, api, security, dependencies:
Cumulative integration against previous candidate phases: PASS/FAIL/PENDING
OpenCode task ID/mode/status: NOT_ASSIGNED unless actually commissioned
Host acceptance: PENDING until real machine review
Remaining P0/P1 and policy decisions:
Decision: RECHECK N (single targeted risk) | AUDIT N+1 | HOLD
May merge? NO without owner authorization. May deploy? NO without host acceptance.
~~~

**فاصل المسؤولية:** إتمام CHAT لإصلاحات N-B لا يعني أن OpenCode نُفّذ أو أن الجهاز المحلي اختُبر. في المراجعة الأمنية المستقلة لا يجوز للمراجع تعديل SHA الخاضع لمراجعته، وأي إصلاح بعد مراجعته يحتاج SHA جديدًا وإعادة اختبار للنطاق المتأثر.
